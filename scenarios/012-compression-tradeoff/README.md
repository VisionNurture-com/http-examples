# 012-compression-tradeoff — 圧縮方式を選ぶための 3 つの目盛り

## 何を測るか

| # | 測るもの |
|---|---|
| ①-g | 水準を上げると何バイト減り、何ミリ秒増えるか |
| ①-h | どの大きさから圧縮が得になるか（下回ると逆効果）|
| ①-i | コンテンツ種別ごとに効き方がどれだけ違うか |

## 埋める欄

決定表 1「コンテンツ種別 × 更新頻度 → 圧縮方式」。

## 判定と、その限界

🔴 **①-g で測るのは「同じ入力に対する圧縮アルゴリズムの費用」であって、サーバの処理能力ではありません。** 同時接続下のスループットは測っていません。CLI の起動時間が混ざらないよう、プロセス内（`node:zlib`）で測ります。

🔴 **①-h は中身の圧縮しやすさで境界が桁で変わります。** 圧縮しやすい標本と、しにくい標本の両方で出し、単一の閾値を提示しません。しにくい側の標本は**種を固定した擬似乱数**で作ります（乱数だと実行のたびに境界が動き、読者が同じ数字を再現できません）。

🔴 **①-i は選んだ標本が結果を決めます。** 種別ごとに**出自を固定した実在ファイル**を複数使い、全件を `summary.json` の `type_samples` に記録してレンジで示します。リポジトリを全走査すると、ファイルが増えるたびに記事の数字が再現できなくなるため、**標本リストを固定**しています。

## 実行

```bash
bash scenarios/012-compression-tradeoff/run.sh
```

サーバもコンテナも要りません。
