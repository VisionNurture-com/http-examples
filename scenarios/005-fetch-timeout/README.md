# 005-fetch-timeout — 応答が返らないとき、クライアントは何秒待つか

## 何を測るか

リトライ条件を決めるには、まず「いつ失敗したことにするか」が要ります。`fetch` に `AbortController` を付けていない場合、**既定では何秒待つのか**を測ります。

## 🔴 測っているのは 2 つあるタイムアウトの片方だけ

応答しないサーバの作り方で、効くタイムアウトが変わります。

| 作り方 | 効くタイムアウト | 本シナリオ |
|---|---|:--:|
| 接続は成立し、**応答を返さない** | 応答待ちのタイムアウト | ✅ 測る |
| **接続そのものが成立しない**（到達しない宛先）| 接続タイムアウト | ❌ 測らない |

足場は `GET /005/never-responds` で、接続を成立させたまま応答を返しません。**「fetch の既定タイムアウト」を 1 つの数字だと思って読むと取り違えます。**

## 🔴 サーバ側が切ったのではないことの確かめ方

Node の HTTP サーバにもタイムアウトの既定値があります。クライアント側の値を測ったつもりでサーバ側の値を測ってしまう取り違えを防ぐため、**同じ足場へ `curl` を当てる対照**を置いています。curl は上限の 330 秒まで切れずに待ち続けました。**サーバが 300 秒で接続を切っていれば、curl もそこで終わっていたはずです。**

## 記事のどこに出るか

決定表「失敗の種類 × 副作用の有無 → 再送可否 / キーの要否」の前段。**リトライ条件を決めるための実効値。**

## 判定

各クライアントが投げたエラーの種類とコードをそのまま記録します。上限で当方が打ち切った場合は「切れなかった」として、エラーの欄を空にします。

## 測れない範囲

- **接続タイムアウト**は測っていません（上記）
- **上限は 330 秒**です。それより長い既定値を持つクライアントがあれば「切れなかった」としか言えません
- ブラウザは別シナリオ（`005-fetch-timeout-browser`）で測ります
- curl 以外の CLI クライアント、および他言語の HTTP ライブラリは測っていません
