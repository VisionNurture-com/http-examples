# 006-navigation — リロードと「戻る」で扱いが変わるか

## 何を測るか

読者が「更新が反映されない」と感じる場面は、リロードと戻るボタンに集中します。この 2 つは別の層で動きます。

- **HTTP キャッシュ層**（リロード・再訪）… Playwright で 3 エンジンを自動計測
- **履歴ナビゲーション層**（戻る）… 実 Chrome を手で操作して計測

分けているのは、**Playwright が既定で bfcache を全ブラウザで無効化する**ためです。Chromium 自身に理由を訊くと `BackForwardCacheDisabledForDelegate` を返し、起動フラグ `--disable-back-forward-cache` を取り除いても解消しません。装置の都合で bfcache を殺した値を「戻ったときの挙動」として載せるわけにはいかないので、この層だけ実ブラウザで測っています。

🔴 **サーバ側の到着記録だけでは bfcache を判定できません。** 戻ったときは bfcache でも HTTP キャッシュからの履歴再利用でもサーバに何も届かないためです（RFC 9111 は履歴機構を仕様の外に置いています）。判別子は `pageshow` イベントの `persisted` です。

## 埋める欄

実効値カード「戻ったときに何が起きるか」の実効値欄。

## 判定

2 系統で判定します。

- ブラウザ内: `pageshow` の `persisted`（[web.dev](https://web.dev/articles/bfcache)）
- サーバ側: ページ自身の到着回数

### 戻るの追試手順（自動化していない部分）

1. Chrome で計測ページを開く
2. コンソールで `addEventListener("pageshow", e => console.log(e.persisted))` を仕込む
3. 別のページへ移動し、戻るボタンを押す
4. `true` が出れば bfcache から復元されている

計測結果は `results/006-navigation/bfcache-manual.json` に、実施条件つきで残しています。

## 対照（測定の事前条件）

測定の前に 3 つの対照を取り、1 つでも崩れたら値を書き出さずに中止します。

| 対照 | 変種 | 崩れたときに疑うこと |
|---|---|---|
| 陰性 | `max-age=600` の 2 回目が 0 件 | そもそもキャッシュが働いていない |
| 陽性 | `no-store` の 2 回目が必ず到着 | 観測チャネル（nginx のログ）が死んでいる |
| 条件付き | `no-cache` の 2 回目が 304 | 「訊きに来たこと」を観測できていない |

3 つ目がないと、「到着 0 件」を「条件付きリクエストすら出さなかった」と読むことができません。沈黙と測定値の区別がつかないためです。
