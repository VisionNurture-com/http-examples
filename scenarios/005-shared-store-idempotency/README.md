# 005-shared-store-idempotency — 処理中のキーを共有ストアに置くと、2 台でも 1 回になる

## 何を測るか

`005-multiprocess-idempotency` は、v07 準拠の実装（B）でも、処理中のキーを覚える置き場所がプロセスの中にあるかぎり、
サーバを 2 台に並べると同じキーの 2 本目を弾けないことを測った。

ここでは**測り方を変えずに、置き場所だけを 2 台から見える所へ移した実装（C）**を並べる。

| 実装 | 処理中のキーの置き場所 | エンドポイント |
|---|---|---|
| A | なし（素朴な実装）| `POST /005/charge-naive` |
| B | プロセス内の `Set` | `POST /005/charge` |
| C | PostgreSQL の主キー（`INSERT … ON CONFLICT DO NOTHING RETURNING`）| `POST /005/charge-pg` |
| C | Redis のキー（`SET … NX PX`）| `POST /005/charge-redis` |

判定の分岐（キーなし 400 / 中身違い 422 / 処理中 409 / 保存済みなら再生）は B と C で同じ。違うのは置き場所だけ。

## 記事のどこに出るか

sec06「自分の API に入れる」。2 台で効かないことを示した表の直後に、直したあとの表として置く。

## 実行モード

**M1**（ブラウザ不要）。CI で回る。

## 測り方

- ロードバランサは挟まない。2 本をそれぞれ別の台へ直接送る
- 課金回数はプロセス内の変数なので、**両方の台から読んで足す**
- 対照として「同じ台へ 2 本」も測る
- 各ケースを **20 回**くり返し、課金回数と応答の組を試行ごとに記録する。合計だけで判定しない
- 試行の前に、各台・各実装へ 1 本ずつ流して共有ストアへの接続を張っておく（結果には数えない）
- `__reset` は両台を呼ぶ。共有ストアは `TRUNCATE` / `FLUSHDB` で空にする（何回呼ばれても同じ状態になる）

## 測っていないこと

- 共有ストアが落ちたとき・遅いときの挙動
- Redis を複数台にした構成やフェイルオーバー（Redis の公式ドキュメントは、`SET NX` による単純なロックより Redlock を勧めている）
- 置き場所どうしの速さの比較
