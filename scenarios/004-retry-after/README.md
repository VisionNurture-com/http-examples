# 004-retry-after — 待ってくれるのは誰か

## 何を測るか

同じ `429 Too Many Requests` + `Retry-After: 3` を 4 種類のクライアントへ返し、**次の要求がいつ届くか**を測ります。

| クライアント | 設定 |
|---|---|
| `curl`（素） | 再試行なし |
| `curl --retry 2` | man に「`Retry-After:` に従う（7.66.0 で追加）」とある |
| Node の組み込み `fetch` | 再試行の設定なし |
| undici `RetryAgent` | 既定で `retryAfter: true`・再試行対象に 429 を含む |

## 判定

🔴 **クライアント側の時刻では測りません。**クライアントのログは自分の実装を測っているだけになります。判定は nginx の到着記録（`$msec`）で行い、**429 を返した時刻と次の到着時刻の差**を見ます。

判定は 3 値です。「再送が来なかった」を「従った」と読まないためです。

| 値 | 意味 |
|---|---|
| `no_retry` | そもそも再送しない |
| `immediate` | `Retry-After` を無視して即座に再送した |
| `waited` | `Retry-After` の秒数だけ待って再送した |

## 汚染対策

レート制限のカウンタはプロセス内に残ります。シナリオの先頭で `POST /004/api/__reset` を叩き、集計はシナリオ開始時刻より後の行だけに限ります。

## 記事のどこに出るか

実効値の表「Retry-After に従うのは誰か」。決定表の「待ってほしいとき、何を返すか」の裏づけ。

## 実行

```bash
bash scenarios/004-retry-after/run.sh
```
