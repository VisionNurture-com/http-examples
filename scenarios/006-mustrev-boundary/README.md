# 006-mustrev-boundary — must-revalidate は期限が切れたあと何を変えるのか

## 何を測るか

`must-revalidate` の有無だけを変えて、**保存したものが期限切れになったあと**の 2 回目に何が届くかを測ります。

`006-contradictory` で測ったのは `max-age=600, must-revalidate` の**期限内**だけで、そこでは 3 エンジンとも到着 0 件でした。ただし仕様が `must-revalidate` に与えている意味は期限内ではなく、**期限が切れたあと**の側にあります。

> once it has become stale, a cache MUST NOT reuse that response to satisfy another request until it has been successfully validated by the origin（RFC 9111 §5.2.2.2）

そこで期限を 5 秒に縮め、7 秒待って境界を跨いでから 2 回目を開きます。`max-age=5` と `max-age=5, must-revalidate` の 2 変種を、有無だけの違いにして比べます。

## 記事のどこに出るか

記事 sec02 / sec03 / FAQ Q3 の「期限が切れたあとの動きは測っていない」という留保。

## 判定

サーバ側の到着記録と status（200 = 取り直した / 304 = 訊きに来たが本体は送られない / 0 件 = 訊きにも来ない）。

## この測定で言えないこと

RFC 9111 が `must-revalidate` で禁じているのは、**再検証に失敗したときに古いものをそのまま出すこと**です。本シナリオはオリジンが正常に応答する経路しか通していないため、**再検証が失敗する場面（オリジンに届かない・エラーを返す）は測っていません**。ここで差が出なかったとしても、それは「オリジンが生きているあいだは差がない」という意味に留まります。

## 対照（測定の事前条件）

`measure-006-cache.mjs` が本測定の前に 3 つの対照を取り、1 つでも崩れたら値を書き出さずに中止します。

| 対照 | 変種 | 崩れたときに疑うこと |
|---|---|---|
| 陰性 | `max-age=600` の 2 回目が 0 件 | そもそもキャッシュが働いていない |
| 陽性 | `no-store` の 2 回目が必ず到着 | 観測チャネル（nginx のログ）が死んでいる |
| 条件付き | `no-cache` の 2 回目が 304 | 「訊きに来たこと」を観測できていない |

本シナリオは **304 と 0 件の区別が結論そのもの**なので、3 つ目の条件付き対照がとりわけ効きます。304 を 1 件も観測できない装置では、期限切れ後の 0 件を「再検証しなかった」と読めません。
