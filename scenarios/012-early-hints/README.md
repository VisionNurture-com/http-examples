# 012-early-hints — 「TTFB が下がった」の見かけと実際

## 何を測るか

103 Early Hints を送ると、報告される TTFB は下がります。**サーバが速くなったからではありません**。ブラウザは最初に届いた応答の時刻を `responseStart` にするため、103 を送った時点で値が決まるからです。

そこで **1 回の遷移から 4 つの値を同時に**取ります。別々の遷移で取ると、揺れなのか差なのか分けられません。

| 値 | 何を表すか |
|---|---|
| `responseStart − startTime` | **報告 TTFB**。ブラウザと RUM ツールが TTFB と呼ぶ値 |
| `finalResponseHeadersStart − startTime` | 最終ヘッダ（200）が届いた時刻 |
| `Server-Timing: app;dur` | **サーバが実際に費やした時間** |
| `eh-asset.css` の `responseEnd` / `loadEventEnd` | **実利得**。読者にとって本当に早くなったか |

## アーム

| 軸 | 値 |
|---|---|
| 経路 | `direct`（アプリ直結・HTTP/1.1 平文）/ `h2direct`（HTTP/2 + TLS）/ `nginx`（nginx 経由・HTTP/2）|
| 103 の中身 | `none`（送らない）/ `bare`（送るがその回の描画に効かない）/ `preload`（実際に使う資源を先読み）|
| 先読み資源の `Cache-Control` | `no-store` / `public, max-age=60` |

🔴 **`bare` が対照の要**です。103 が「速さ」ではなく「最初の応答の時刻」を動かしているだけなら、**描画に何の役にも立たない 103 でも報告 TTFB は同じだけ下がる**はずです。

🔴 **`Cache-Control` を振る理由**は、「先読みしたのに速くならない」ときに**ブラウザが先読みを活かさないのか、保存できない応答なので取り直しているのか**を分けるためです。

🔴 **試行ごとに資源の URL を変えます**。保存可能な資源を同じ URL で繰り返し測ると、2 回目以降はキャッシュから返り、先読みの効果が消えます（実際に 1 度これで誤った表を作りました）。

## 実行

```bash
bash scenarios/012-early-hints/run.sh
```

🔴 **app を作り直したら edge も再起動してください。** nginx は上流の IP を起動時に解決するため、作り直した app へは 502 を返し続けます。run.sh は先頭で再起動します。
